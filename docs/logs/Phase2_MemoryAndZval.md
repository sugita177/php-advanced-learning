## Lesson 2.1: 配列と変数の Copy on Write (COW) 挙動の検証

- **検証日**: 2026-09-27
- **検証コード**:
  - 実証スクリプト: `src/Phase2/Lesson2_1_CopyOnWrite.php`
  - Pestテスト: `tests/Unit/Phase2/Lesson2_1_CopyOnWriteTest.php`

### 1. 検証した言語仕様・テーマ
- Zend Engine のメモリ最適化の中核である **Copy on Write (COW: 書き込み時コピー)** 機構。
- 変数代入 (`$b = $a`) 時の参照カウンタ (`refcount`) のインクリメントと物理メモリ共有。
- 配列要素の書き換え（Write）発生時におけるメモリの遅延ディープコピー。
- 関数への配列の「値渡し」における COW 挙動（読み取り専用ならコピーゼロ）。
- 関数スコープ脱出時におけるローカル変数の即時解放（ライフサイクル）とメモリ回収。

### 2. 実施したテスト・検証概要
- 100,000 要素の整数配列（約 2.1 MB）を用いた `memory_get_usage()` 計測：
  1. **配列作成**: 2,101,328 bytes (約 2.00 MB) を消費。
  2. **単純代入 (`$b = $a`)**: メモリ増加は **0 bytes**（同じバッファを指すため複製なし）。
  3. **要素書き換え (`$b[0] = 999`)**: メモリが **2,101,328 bytes** ドカンと増加（ここで初めて丸ごと複製）。
  4. **値の独立性**: `$a[0] === 1`, `$b[0] === 999` であり、相互に影響しないことを確認。
  5. **読み取り専用関数への値渡し**: メモリ増加は **0 bytes**（値渡しでも読み取りだけならコピーは一切発生しない）。
  6. **関数内での書き換えと解放**:
     - 関数内部で `$data[0] = 11;` を実行した瞬間は **2,101,328 bytes** 複製される。
     - しかし関数を抜けてスコープを脱出した瞬間、外部で参照を持たないコピーは即座にメモリ解放され、呼び出し元のメモリ使用量は元通りに戻る。

### 3. 直面した落とし穴・内部挙動の気付き
- **「関数に渡すとコピーされる」という誤解（上級試験の最頻出罠）**:
  - C言語等の感覚で「巨大配列は参照渡し (`&`) にしないとメモリが爆発する」と考えがちだが、PHP では値渡しでも内部的には代入と同じ COW が効くため、読み取り専用であればコピーコストはゼロである。
- **関数内での計測とスコープ脱出による即時解放の落とし穴**:
  - 関数の外側で「関数呼び出し後のメモリ」を測っても、関数スコープを抜けた瞬間に複製された配列が解放されて差分が `0` になる。関数内で COW が起きたことを証明するには、関数内部で計測して返すか、関数の戻り値として変数で受け取って参照を保持し続ける必要がある。

### 4. 実務・Qiita 向けのアウトプット要点
- 「メモリ節約のため」という理由だけで不用意に関数の引数に参照渡し (`&`) を使ってはならない。PHP の COW に任せて普通に値渡しをする方が安全で、バグも生まず、メモリ効率も同等である。
- 配列を書き換える処理を関数に切り出す場合、その関数が実行されている瞬間だけ一時的にメモリが倍増（COW）することを意識したメモリ設計を行う。

## Lesson 2.2: 参照渡し (&) が COW に与える影響と参照の分離・foreach の罠

- **検証日**: 2026-09-28
- **検証コード**:
  - 実証スクリプト: `src/Phase2/Lesson2_2_ReferencesAndCow.php`
  - Pestテスト: `tests/Unit/Phase2/Lesson2_2_ReferencesAndCowTest.php`

### 1. 検証した言語仕様・テーマ
- 参照代入 (`$b = &$a`) における内部構造（`IS_REFERENCE` と `zend_reference` 構造体）。
- 参照関係にある変数への書き換え時における COW（メモリ複製）のスキップ。
- 参照と通常代入が混在した際における「参照の分離（Reference Separation）」と COW 発生。
- `foreach ($array as &$val)` のスコープ漏れによる配列破壊バグ（上級試験の超最頻出トラップ）。
- `unset()` による参照の明示的デタッチ（解除）の必須性。

### 2. 実施したテスト・検証概要
- 参照とメモリ:
  - `$b = &$a` の後、`$b[0] = 999` と書き込んでもメモリ複製（2MB）は発生せず、`$a[0]` も連動して 999 になることを検証。
- 参照の分離:
  - `$b = &$a`（参照ペア）に対し、`$c = $a`（通常代入）を行った後、`$c[0] = 777` と書き換えると `$c` のみで COW 複製（2MB）が発生し、`$a` と `$b` は無傷であることを検証。
- 恐怖の foreach 参照破壊:
  - `foreach ($numbers as &$val)` で要素を 2 倍にした後、連続して `foreach ($numbers as $val)` を回すと、配列の最後の要素が破壊されて `[2, 4, 4]` に化ける現象を完全再現。
- `unset()` の救済:
  - 1回目のループ直後に `unset($val)` を実行することで、配列が `[8, 10, 12]` と正常に保持されることを検証。

### 3. 直面した落とし穴・内部挙動の気付き
- **なぜ `[2, 4, 4]` に化けるのか**:
  - PHP の `foreach` はブロックスコープを作らないため、ループ終了後も変数 `$val` は `$numbers` の最後の要素（`$numbers[2]`）への参照を保持したまま生存する。
  - 2 回目のループで各要素が `$val` に代入されるたびに、参照先である `$numbers[2]` が逐次上書きされてしまう。1周目で `2` が入り、2周目で `4` が入り、3周目は自分自身（`4`）を代入するため、最後の `6` が完全に消失する。
- **`&int(4)` の正体**:
  - `var_dump` で最後の要素に `&` が付くのは、Zend Engine 内部でその要素が依然として外部の `$val` と `zend_reference` 構造体を共有（refcount: 2）している証拠である。
  - `unset($val)` を呼ぶと参照カウンタが 1 に減り、不要になった `zend_reference` が解体されて通常の純粋な `int` に復帰する。

### 4. 実務・Qiita 向けのアウトプット要点
- 参照渡しを使った `foreach ($array as &$item)` を記述した直後は、**一行の例外もなく直後に `unset($item);` を書くことをチームの絶対規約** とする。
- そもそも現代 PHP では、参照渡しによる破壊的ループの代わりに `array_map()` や第一級 Callable、イミュータブルなコレクション操作を採用することで、参照バグの発生余地を根本から排除するのがモダン設計の定石である。

## Lesson 2.3: 循環参照と gc_collect_cycles() の内部挙動・デストラクタの遅延

- **検証日**: 2026-09-29
- **検証コード**:
  - 実証スクリプト: `src/Phase2/Lesson2_3_CircularReferencesAndGc.php`
  - Pestテスト: `tests/Unit/Phase2/Lesson2_3_CircularReferencesAndGcTest.php`

### 1. 検証した言語仕様・テーマ
- 参照カウント方式（Reference Counting）の限界と「循環参照（Circular Reference）」によるメモリリークの発生機構。
- オブジェクトのライフサイクルと `__destruct()` の呼び出しタイミング。
- Zend Engine の Concurrent Cycle Collection（同期サイクル収集）アルゴリズム。
- GC ルートバッファと `gc_collect_cycles()` による強制回収。
- テストにおける時系列アサーション（`not->toContain` による遅延検証）と、Pest の `toBeIn` による非決定論的順序の吸収。

### 2. 実施したテスト・検証概要
- 通常オブジェクトの破棄:
  - 単純なオブジェクト `$nodeA` は `unset()` された瞬間に即座にデストラクタが走り、`Point 1` の前に解放されることを検証。
- 循環参照オブジェクトの遅延破棄:
  - `$b1` と `$b2` が相互参照している場合、外側の変数を `unset()` しても参照カウンタが 1 残るため、`Point 2` の時点ではデストラクタが走っていない（遅延している）ことを `expect()->not->toContain()` で検証。
  - `gc_collect_cycles()` を実行した瞬間に、回収数（`> 0`）が返り、ここで初めてデストラクタが発火して `Point 3` の前に両ノードが解放されることを検証。
  - GC の内部探索順序によるノード解体順（B1→B2 または B2→B1）を `toBeIn([$pattern1, $pattern2])` で柔軟かつ厳密にアサーション。

### 3. 直面した落とし穴・内部挙動の気付き
- **変数のスコープとテスト記録**:
  - デストラクタ内からテスト側の配列へログを書き込む際、通常ローカル変数やグローバル変数ではスコープが途切れるため、クラスの静的プロパティ（`public static array $messages`）を経由する必要があることを学んだ。
- **循環参照はプロセス終了まで解放されないリスク**:
  - 短命な Web リクエスト（1リクエスト 1プロセス）ではスクリプト終了時に全メモリが一括解放されるため目立ちにくいが、長時間稼働するデーモン、Worker、バッチ処理、Swoole/RoadRunner などの常駐型 PHP アプリケーションでは、循環参照が蓄積すると致命的な OOM（Out Of Memory）を引き起こす。

### 4. 実務・Qiita 向けのアウトプット要点
- 長時間稼働する PHP プロセス（キューワーカー、CLI バッチ）では、定期的に `gc_collect_cycles()` を手動実行するか、循環参照を作らないオブジェクト設計（親子関係での弱参照の活用）が必須となる。
- 双方向リンクや親子リレーション（Parent-Child）を構築する際は、次の Lesson 2.4 で扱う `WeakReference` を採用することで、循環参照の輪を物理的に断ち切るのが現代のベストプラクティスである。

## Lesson 2.4: WeakReference と WeakMap によるメモリリーク抑止

- **検証日**: 2026-09-29
- **検証コード**:
  - 実証スクリプト: `src/Phase2/Lesson2_4_WeakReferenceAndMap.php`
  - Pestテスト: `tests/Unit/Phase2/Lesson2_4_WeakReferenceAndMapTest.php`

### 1. 検証した言語仕様・テーマ
- 強参照（Strong Reference）と弱参照（Weak Reference）の決定的な違い（参照カウンタ `refcount` を増やさない）。
- `WeakReference::create()` による弱参照の生成と、オブジェクト破棄後の安全な `null` 返却 (`get(): ?object`)。
- 親子ノード（Parent-Child）や双方向ツリー構造における循環参照の根絶。
- PHP 8.0 `WeakMap` による、オブジェクトのライフサイクルと完全に連動した自動エントリ消滅（Garbage Collection）キャッシュ機構。

### 2. 実施したテスト・検証概要
- 弱参照のライフサイクル:
  - `$user` 生存中は `$ref->get()` で同一インスタンスが取得でき、`unset($user)` 直後はエラーにならず安全に `toBeNull()` になることを検証。
- 親子双方向リンクの即時解放:
  - 親が子を強参照し、子が親を `WeakReference` で保持する構造を作成。
  - `unset($parent)` した瞬間、GC のサイクル収集を待つことなく即座に `ParentNode` のデストラクタが走り、循環参照が物理的に発生していないことを証明。
- WeakMap の自動蒸発:
  - 2つのエンティティをキーに登録（`count === 2`）。
  - `$entity1` を `unset()` した瞬間に、手動削除なしでマップからエントリが自動消滅（`count === 1`）し、残存する `$entity2` のみ有効であることを検証。

### 3. 直面した落とし穴・内部挙動の気付き
- **破棄後の安全設計（エラーではなく null）**:
  - C言語のダングリングポインタのようなクラッシュを起こさず、参照先が消滅した場合は静かに `null` を返すため、呼び出し側は安全に生存確認ができる。
- **WeakMap が解決した歴史的課題**:
  - 従来の PHP でエンティティの外部メタデータやキャッシュを配列（`$cache[spl_object_id($obj)]`）に持つと、配列自体が参照を握り続けるためオブジェクトが永遠にメモリ解放されないリークが発生していた。`WeakMap` により、キーのオブジェクト破棄と同時にキャッシュも自動消滅する完全なメモリ安全性が実現された。

### 4. 実務・Qiita 向けのアウトプット要点
- 双方向リレーション、イベントリスナーの登録解除、オブザーバーパターンなど、オブジェクトの循環が発生しやすい箇所には `WeakReference` を第一選択肢とする。
- ORM の変更追跡（Unit of Work）や一時的なメタデータキャッシュには `WeakMap` を活用することで、手動クリーンアップ不要の堅牢なアーキテクチャを構築する。
